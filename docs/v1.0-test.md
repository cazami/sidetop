# 6つ目：モニターが2台以上のときは止まる（版 0.4.7）

マルチモニター（仕様書 3.7）は v1.1 に回しました（2026-10-31、ユーザーの判断）。それまでのあいだ、2台以上の環境で配置を崩さないための処理です。

## 変わったこと

- 起動したときにモニターが2台以上なら、mod は止まったままでいます。ログに `WARNING: 2 monitors. Sidetop supports only one so far and stays off.` と出ます。
- 動いているあいだも、1秒ごとにモニターの数を見ます。
  - 2台以上になったら、すべてのアイコンをホームに戻してから止まります（mod を無効にしたときと同じです）。ログに `WARNING: 2 monitors now. Sidetop stops.` と出ます。
  - 1台に戻ったら、また動き出します。ログに `One monitor again. Sidetop starts.` と出ます。
- モニターが2台以上のあいだは、作業領域を広げません。モニターを足した瞬間から、Explorer がアイコンを画面の中に保ちます。
- README と mod の説明にも書きました。
- 確かめたこと（Claude）：64 ビットと 32 ビットでコンパイルとリンクが通ること。2台の場合は、モニターが1台の実機では確かめられません。

## 確かめること

| # | 確かめること |
|---|---|
| MA | モニター1台で、今までどおり動くか（ホイール、中ボタンドラッグ、ホームへ戻る、ドラッグ中の自動スクロール） |
| MB | 右のページにアイコンを置いたまま、mod を無効にしてから有効に戻す。今までどおりか |
| MC | （2台の環境、たとえば仮想マシンで画面を2つにして）2台のまま mod を有効にする。止まったままで、アイコンが動かないか |
| MD | （2台の環境）1台で右のページにアイコンを置いてから、2台目を足す。すべてのアイコンが見える場所に戻り、止まるか |
| ME | （2台の環境）2台目を外す。また動き出すか |

MC〜ME は、VirtualBox の仮想マシンで「モニター数」を2にすると試せます。

# 5つ目：ホームへ戻るショートカットキー（版 0.4.6）

仕様書 5 章の「ホームへ戻る操作（ダブルクリック / ショートカットキー / なし）」です。

## 変わったこと

- 設定「Double-click an empty spot to go back home」（オン／オフ）をなくし、次の2つにしました。
  - **Go back home with**：Double-click on an empty spot（既定）／ Shortcut key ／ Nothing。
  - **Shortcut key for going back home**：既定は `Ctrl+Alt+Home`。
    - Ctrl、Alt、Shift、Win を `+` でつなぎ、最後にキーを1つ書きます。
    - 書けるキーは、英字、数字、F1〜F24、Home、End、PageUp、PageDown、Insert、Delete、Left、Right、Up、Down、Space、Backspace です。
    - 大文字と小文字は区別しません。前後の空白は無視します。
- ショートカットキーは、どのウィンドウを開いていても効きます（`RegisterHotKey`）。押し続けても繰り返しません。
- ほかのプログラムがすでに同じキーを使っているときは、使えません。そのときはログに `WARNING: cannot use the home shortcut` と出ます。読めない書き方のときは `WARNING: cannot read the home shortcut` と出ます。
- 確かめたこと（Claude）：
  - 64 ビットと 32 ビットでコンパイルとリンクが通ること。
  - キーの書き方を読む部分を取り出して、いくつかの書き方で正しく読めること。
  - この PC では、`Ctrl+Alt+Home`、`Win+Alt+H`、`Ctrl+Win+Home` がどれも空いていること。

## 確かめること

設定を変えたら「Save settings」を押します。mod が設定を読み直します。

| # | 確かめること |
|---|---|
| HA | 設定を変えずに入れる。今までどおり、空き部分のダブルクリックでホームへ戻るか。`Ctrl+Alt+Home` では何も起きないか |
| HB | 「Shortcut key」にする。右のページで `Ctrl+Alt+Home` を押すとホームへ戻るか。ダブルクリックでは戻らないか |
| HC | ほかのウィンドウ（メモ帳など）を前に出したまま `Ctrl+Alt+Home` を押す。ホームへ戻っているか（Win+D などでデスクトップを見て確かめます） |
| HD | キーを `Win+Alt+H` などに変えて Save。新しいキーで戻り、前のキーでは何も起きないか |
| HE | キーを `Ctrl+Alt+Foo` のような読めないものにして Save。何も起きず、ほかの動きに影響がないか（ログに WARNING が出ます） |
| HF | 「Nothing」にする。ダブルクリックでもキーでも戻らないか |
| HG | 「Shortcut key」のまま mod を無効にしてから有効に戻す。キーが今までどおり効くか |
| HH | 離散モード（Page by page）で、キーでホームへ戻るか |

## 結果（2026-10-31、ユーザーの実機、0.4.6）

HA〜HH、すべて OK でした。

# 4つ目：アイコンが多いところの軽量化（版 0.4.5）

ユーザーの依頼（2026-10-31）：「アイコンが多いところでの軽量化を、大きな変更なしにできないか」。ユーザーが寝ているあいだに、Claude が Windhawk を通さずに測って決めました。x64 と x86 の両方で、リンクまで通っています。0.4.5 そのものは、実機の Windhawk ではまだ動かしていません。

## 測り方

`tools/lvprof.cpp` を作りました。wallprobe と同じく、`SetWindowsHookEx` でデスクトップのスレッドに一時的に読み込み、ListView と DefView をサブクラス化して時間を測ります。

- 1コマ（ListView の `WM_PAINT`）を、背景（DefView の `WM_PRINTCLIENT`）、DefView への問い合わせ（`WM_NOTIFY` の種類ごと）、残り（ListView 自身の描画）に分けます。
- 実際のスクロール（入っている mod に、ホイールのメッセージを送ります）と、ホームで止めたまま画面全体を30回描き直す「ベンチ」の2通りで測りました。
- 測ったのは Wide image（テスト画像）のときです。アイコンは 52 個です。

## 分かったこと

ベンチ（アイコン 52 個がすべて見えている画面を1回描き直す）の結果です。

| 条件 | 1回 | 問い合わせ | ListView 自身 | 背景 |
|---|---|---|---|---|
| 今まで | 170 ms | 92 ms（104 回） | 76 ms | 1.6 ms |
| 問い合わせの答えを覚えて返す | 61 ms | 0.05 ms | 59 ms | 1.6 ms |
| ＋文字の影を消す（使わない） | 56 ms | 0.08 ms | 54 ms | 1.5 ms |
| ＋ListView の消去を省く（効果なし） | 62 ms | 0.06 ms | 60 ms | 1.6 ms |
| ＋二重バッファを外す（使えない） | 102 ms | 0.06 ms | 100 ms | 2.7 ms |

- 問い合わせは `LVN_GETDISPINFOW` です。デスクトップの ListView は owner-data なので、見えている項目ごと、1コマごとに、DefView へ2回尋ねます（1回目は文字だけ（mask 0x1、幅を測るため）、2回目は文字・アイコン・状態（mask 0xB、stateMask 0xF00 は重ね絵））。1回に約 0.9 ms かかります。アイコンが多い画面では、これが重さの半分以上でした。
- 実際のスクロールでも、1コマの最大は毎回 180〜250 ms（ホーム付近）でした。
- 文字の影は約 8% でしたが、見た目が変わるので使いません。二重バッファを外すと、背景が描かれず、かえって重くなりました。
- 残る ListView 自身の描画は、アイコン1個あたり約 1.1 ms です。見た目を変えずにここを減らすには、アイコンの絵を丸ごと覚えて合成する、大きな作りが要ります。今回は見送りました。
- Wide image のときは、壁紙もアイコンと一緒に動きます。そのため、古い絵をコピーしてずらしても正しく見えます（`SWP_NOCOPYBITS` を外す）。実際のスクロールで、1コマ平均 27 ms が 9 ms に、問い合わせの答えを覚えるのと合わせると 5.6 ms になりました。途中で止めて撮った画面でも、目盛り、アイコン、矢印に崩れはありませんでした。

## もっと大きな原因：PC 全体で、ウィンドウ管理の呼び出しが遅かった（00:45〜00:55 ごろ）

ListView 自身の描画（52 個で約 60 ms）の中身を、サンプリングで調べました（`lvprof` のフラグ 256。デスクトップのスレッドを約 1 ms ごとに一瞬止めて、実行中の場所とスタックを記録します）。

| 一番内側の関数 | 割合 | 呼び出し元 |
|---|---|---|
| `NtUserGetProp` | 30.8% | comctl32 のサブクラスの仕組み（`MasterSubclassProc`）。メッセージ1通ごとに呼びます |
| `NtUserGetDC`＋`NtUserReleaseDC` | 22.4% | comctl32 の `CImageListBase::GetOverlayBoundingRectForDPI`。重ね絵（ショートカットの矢印など）を描くたびに、`SHGetCurColorRes` と `ComputeSystemDPI` が `GetDC(NULL)` で画面の色数と DPI を調べ直します |
| 文字の整形（TextShaping）など | 約 10% | |
| `BitBlt`、`AlphaBlend` | 9.6% | |

`GetProp` と `GetDC` を、それぞれ 1 回ずつ測りました。

| 呼び出し | Explorer の中 | 別のプロセス（`tools/syscalls.cpp`） | ふつう |
|---|---|---|---|
| `GetProp` | 267〜285 µs | 270〜310 µs | 1 µs 未満 |
| `GetDC`/`ReleaseDC` | 223 µs | 190〜230 µs | 数 µs |
| `GetWindowLong`、`GetClientRect`（カーネルに入らない） | | 0.01 µs | |

- **カーネルのウィンドウ管理（win32k）に入る呼び出しだけが、PC 全体で数百倍遅くなっていました。** Explorer や Sidetop に限った話ではありません。
- そのとき、**Cakewalk Sonar（PID 38068）の1本のスレッドが、CPU 1個のほぼ 95% をカーネルの中で使い続けていました**（ほかのプロセスはほとんど使っていません）。win32k の中のロックを握り続けているため、ほかのプロセスの呼び出しが待たされていると見ています。
- Windhawk の「進行中の Mod タスク」の窓には、別の mod `slick-window-arrangement` が Sonar.exe（PID 38068）の中で「未初期化中」のまま止まっていると出ていました。関係があるかもしれません。
- Sonar には保存していない作業があるかもしれないので、Claude は止めたり触ったりしていません。**Sonar を閉じて（または slick-window-arrangement を外して）から測り直すと、本当の重さが分かります。** そのときは `tools/syscalls.cpp` で、`GetProp` が 1 µs 未満に戻っているかを先に確かめます。
- この遅さの中では、問い合わせ（`LVN_GETDISPINFOW`）の 0.9 ms も、DefView の中の同じ種類の呼び出しで膨らんでいる可能性があります。ふつうの状態では、どの数字ももっと小さいはずです。それでも、問い合わせの答えを覚えて返すことと、Wide image で古い絵をコピーすることは、仕組みの上で描く量そのものを減らすので、ふつうの状態でも効きます。
- この遅さを受けて、mod では、問い合わせのたびにアイコンの数を確かめるのをやめ、1コマに1回にしました（`LVM_GETITEMCOUNT` は ListView のサブクラスを通るので、この状態では1回 0.3 ms かかります）。
- **00:58 に測り直すと、`GetProp` は 3.7 µs、`GetDC`/`ReleaseDC` は 20 µs に戻っていました。Sonar は終わっていました**（Claude は触っていません）。メインウィンドウがなく、カーネルで回り続けていたので、終了の途中で止まっていたのだと見ています。

## ふつうの状態で測り直した結果（00:59〜）

| 条件 | ベンチ（ホーム、52 個すべて） | 実際のスクロール（平均 / 最大） | 描いた面積 |
|---|---|---|---|
| 今まで | 30.6 ms | 12.6 / 43〜54 ms | 画面全体 |
| 問い合わせの答えを覚えて返す | 24.9 ms（−19%） | 11.7 / 50 ms | 画面全体 |
| 古い絵をコピー（Wide image） | | 1.5 / 12 ms | 0.04M px |
| 両方（Wide image） | | 1.4 / 21 ms | 0.04M px |

- ふつうの状態では、ホームの描き直しは 170 ms ではなく 31 ms でした。今夜「重い」と測った分の大部分は、上の PC 全体の遅さによるものです。
- ユーザーがこれまで重いと感じていたときに、同じ状態（終わりかけの Sonar など）だったかどうかは分かりません。
- ふつうの状態での ListView 自身の描画（約 26 ms）の内訳は、次のとおりです（サンプリング）。どれも、まっとうな描画の仕事です。
  - 文字の整形と描画：TextShaping 14%、`ExtTextOut` 8.7%、フォント関係 10% ほど
  - アイコンの絵：`BitBlt` 10.7%、`AlphaBlend` 9.2%
  - `GetProp`：6.7%
- Fixed と Parallax のときに、これ以上大きく軽くするには、アイコンの層を丸ごと絵として覚えて合成する作りが要ります（大きな変更）。今回は見送りました。

## 変わったこと（0.4.5）

- デスクトップが動いているあいだ（ホイールの動き、中ボタンドラッグ、端での自動スクロール）は、DefView が `LVN_GETDISPINFOW` に答えた内容を覚えておき、同じ問いには覚えた答えを返します。

  - 覚えた答えを使ったときは、止まってから 0.3 秒後に、画面をもう一度ふつうに描き直します。動いているあいだに名前やアイコンが変わっていても、ここで正しくなります。ホーム付近では、この1回に今までどおり 170 ms ほどかかります。
- Wallpaper が Wide image で画像を読めているときは、古い絵をコピーしてずらします。新しく見えてきた帯だけを描きます。

# 3つ目：壁紙の3モード（版 0.4.4）

仕様書 3.5 です。x64 と x86 の両方で、リンクまで通っています。実機ではまだ動かしていません。

## 分かったこと（shell32 のシンボルと逆アセンブル、2026-10-30）

- デスクトップの壁紙は、`CDesktopBrowser::PaintWallpaper(HWND, HDC)`（仮想関数）が描いています。中では `CDesktopWallpaper::PaintWallpaper` を呼び、画面上の位置に合わせて描きます。壁紙がない（単色）ときは、`GetSysColor(COLOR_BACKGROUND)` で塗るだけです。
- ListView（comctl32）は `PaintDesktop` を使っていません。`DrawThemeParentBackground` で、背景を親に描かせています。ListView をずらしても壁紙が止まって見えるのは、このためです。
- `PaintWallpaper` は、ほかにも、メモリ上の DC に壁紙を写す処理（shell32+0x189803）から呼ばれています。

結果（0.4.4、2026-10-31）：WA、WB、WC、WE、WF、WG、WH は OK。WD は、アイコンが多いと重いものの、Fixed のときと変わらないので OK。

- ログでは `Wallpaper behind SHELLDLL_DefView is painted through WM_PRINTCLIENT` が出ました。
- Parallax で壁紙を変えたときは、`LoadWallpaper` が新しい画像を読み込み直していました（WF）。

## 0.4.2 の結果と 0.4.3 の修正（2026-10-31）

- WB でだめでした。壁紙が変わりませんでした。
- ログで分かったこと：
  - 画像は読み込めていました（`wide-test.png: 3840x1080 -> 3840x1080`）。
  - ただ、`PaintWallpaper` のフックは、デスクトップの描画で一度も呼ばれていませんでした（`Explorer paints the wallpaper for ...` が一度も出ませんでした）。
  - 設定を保存した最初の1回は `CreateDecoderFromFilename failed (80070002)`（ファイルがない）でした。パスを打っている途中で保存されたためと見ています。
- 見込み：ListView は `DrawThemeParentBackground` で背景を親に描かせます。親から先は、デスクトップのウィンドウの既定の処理が、Windows の内部（win32k）で壁紙を描いているようです。`CDesktopBrowser::PaintWallpaper` は、壁紙を切り替えるときのフェードなど、別の場面のためのものと見ています。
- 修正（0.4.3）：`DrawThemeParentBackground`（uxtheme）をフックしました。デスクトップの ListView からの呼び出しのときだけ、自分の画像を描きます。`PaintWallpaper` のフックも残してあります。
- 確かめること：ログに `Wallpaper behind SysListView32 is painted through DrawThemeParentBackground` が出るか。出れば、この経路で合っています。

## 0.4.3 の結果と 0.4.4 の修正（2026-10-31）

- WB はまたしてもだめでした。ログには `Wallpaper behind ...` が一度も出ず、`DrawThemeParentBackground` も使われていませんでした。
- comctl32（6.0.19041.6456）のシンボルを取って調べました。ListView の背景を描くのは `CLVBackgroundManager::DrawSimpleBackground` です。背景色が `CLR_NONE` のとき、次のように描いています。
  1. DC の原点を親（DefView）の座標へずらす（`MapWindowPoints`、`OffsetWindowOrgEx`）。
  2. `LVS_EX_TRANSPARENTBKGND`（デスクトップの ListView には付いています）なら、親へ `WM_PRINTCLIENT`（lParam = `PRF_ERASEBKGND`）を送る。
  3. それが 0 を返したら、`WM_ERASEBKGND` を送る。
  4. DC の原点を戻す。
- つまり、関数ではなくメッセージで親に描かせていました。修正（0.4.4）：DefView をサブクラス化し、この2つのメッセージのときに自分の画像を描くようにしました。効いたことのない `DrawThemeParentBackground` のフックは外しました（`PaintWallpaper` のフックは残してあります）。
- **Windhawk を通さずに確かめました。** Windhawk のエディタは Claude からは貼り付けができず、編集中のファイル（`C:\ProgramData\Windhawk\EditorWorkspace\mod.wh.cpp`）も一般ユーザーには書けません。そこで `tools/wallprobe.cpp` を作りました。`SetWindowsHookEx(WH_GETMESSAGE)` でデスクトップのスレッドにだけ一時的に読み込み、mod と同じ計算で DefView をサブクラス化して、テスト画像を描きます。決めた秒数が過ぎると、サブクラスを外してから抜けます。
  - ホーム：0、480、960、1440 の目盛りが、アイコンの後ろに出ました。
  - 右のページ（ずらし量 1920）：1920〜3360 の目盛りが出ました。

## 変わったこと

- 設定「Wallpaper」で、次の3つから選べます。
  - Fixed（既定）：今までどおり、壁紙は動きません。
  - Parallax：今の壁紙が、アイコンの 20% の速さで動きます。1ページ分動かすと、壁紙は 384 px 動きます。
  - Wide image：設定「Wide image file」の画像を、ホームと追加のページを合わせた幅（今は 3840×1080）に広げて、アイコンと一緒に動かします。
- 画像は、縦横比を保ったまま、隙間なく覆う大きさに広げます。はみ出した分は、左右か上下を同じだけ切ります。
- DefView をサブクラス化し、ListView が背景を頼んだとき（`WM_PRINTCLIENT` と `WM_ERASEBKGND`）に、自分で用意した画像をずらして描きます（0.4.4 から）。mod が動いていないときや Fixed のときは、Explorer に任せます。
- Parallax のときは、2秒に1回まで、壁紙のファイルと更新日時を確かめます。壁紙を変えたときやスライドショーでも、新しい画像に入れ替えます。

# 2つ目：離散モード（版 0.4.1）

仕様書 3.3 の「1ページ（1画面幅）単位で移動し、止めたときにページ境界へ吸着する」です。

結果（2026-10-30）：確かめられるものはすべて OK（DG はタッチパッドがないため未確認の可能性あり）。

## 変わったこと

- 設定「Scrolling」で、「Smooth」（今までどおり、既定）と「Page by page」を選べます。
- Page by page のときは、次のように動きます。
  - ホイール：1ノッチで1ページ動きます。タッチパッドなどの細かい量は、足して1ノッチ分になったら1ページ動きます。0.4 秒あくか、向きが変わると、足した分は捨てます。
  - チルトと横スワイプ：ホイールと同じです。
  - 中ボタンドラッグ：ドラッグ中は手に付いてきます。離すと、始めたページから4分の1ページ以上動かしていれば、その方向のページへ吸着します。それより少なければ、元のページへ戻ります。
  - ドラッグ中の自動スクロール：端で 0.5 秒止めると、次のページへ動きます。止め続けると、着いてからまた 0.5 秒で次へ進みます（ページが2つ以上のとき）。v0.3 の第1版と同じ動きです。少しずつ動かして止まった位置で吸着させると、置いたばかりのアイコンが画面の外へ出てしまうためです。
  - ダブルクリックでホームへ戻るのは、今までどおりです。
  - Explorer の起動時に前の位置へ戻すときも、ページの区切りに合わせます。
- 動きの速さは、今までの「Glide」の設定に従います。0 にすると一瞬で切り替わります。

## 確かめること

| # | 確かめること |
|---|---|
| DA | 設定を Page by page にする。ホイールを1ノッチ回すと、ちょうど1ページ動き、ページの区切りで止まるか |
| DB | ホイールを速く何ノッチも回したときに、行き過ぎたり、半端な位置で止まったりしないか |
| DC | 中ボタンドラッグで少しだけ動かして離すと、元のページへ戻るか。4分の1ページより多く動かして離すと、次のページへ吸着するか |
| DD | アイコンをドラッグして端で止めると、ページ単位で動くか。ドロップした位置は合っているか |
| DE | Page by page のまま Explorer を再起動しても、ページの区切りで始まるか |
| DF | 設定を Smooth に戻すと、今までどおりの動きに戻るか |
| DG | タッチパッドがあれば、横スワイプで1ページずつ動くか（なければ飛ばします） |

ログでは `Settled at ...`（止まった位置。ページの区切りなら 0 か 1920）と、`Auto-scroll: 0 -> 1920` の行を見ます。

# 1つ目：位置インジケーター（版 0.4.0）

仕様書 3.6 です。

結果（2026-10-30）：最初は gdi32 のリンク漏れでコンパイルできませんでした（70c7da0 で修正）。直したあとは IA〜IH すべて OK。

## 変わったこと

- デスクトップが動いているあいだ、画面の下（タスクバーのすぐ上）の真ん中に、細いバーを出します。
  - 薄い灰色の溝の上に、白いつまみが乗った形です。つまみの位置が、今見ている場所です（左端がホーム）。
  - 大きさは幅 160 px、高さ 4 px です（100% のとき。DPI に合わせて大きくなります）。
- 止まってから 0.5 秒はそのまま見せ、0.25 秒かけて消えます。
- 出るのは、ホイール、中ボタンドラッグ、ダブルクリックでホームへ戻るとき、ドラッグ中の自動スクロールのときです。Explorer の起動時に前の位置へ戻すときや、mod を止めるときには出ません。
- 設定「Show a position bar at the bottom while scrolling」（既定オン）で消せます。

## 仕組み

- バーは、デスクトップのウィンドウ（Progman）が持ち主の、小さな半透明のウィンドウです（`WS_EX_LAYERED`）。持ち主より手前、ふつうのウィンドウより奥に出ます。そのため、ほかのアプリの上には出ません。
- クリックは素通りします（`WS_EX_TRANSPARENT`）。タスクバーや Alt+Tab にも出ません（`WS_EX_TOOLWINDOW`）。
- 消えたあとはウィンドウを片付け、次に出るときに作り直します。タスクバーの位置や DPI が変わっていても、そのときの位置に出ます。

## 確かめること

| # | 確かめること |
|---|---|
| IA | ホイールで右へ動かすと、画面の下にバーが出て、つまみが右へ動くか。止まると少しして消えるか |
| IB | 見た目は細く控えめで、Windows の雰囲気を崩していないか。明るい壁紙と暗い壁紙の両方で見えるか |
| IC | 中ボタンドラッグ、ダブルクリックでホームへ戻る、ドラッグ中の自動スクロールでも出るか |
| ID | バーが出ているあいだも、その下のアイコンやデスクトップをクリックできるか |
| IE | ウィンドウを開いているときに、バーがそのウィンドウの上に出ないか |
| IF | 動きの滑らかさが、前（0.3.6）より落ちていないか |
| IG | 設定でオフにすると出なくなるか |
| IH | タスクバーの位置や大きさを変えたあとも、タスクバーのすぐ上に出るか |

ログでは `Indicator ...` の行（作れなかったときだけ出ます）と、`Settled at ...` の行の frames と avg（1コマにかかった時間）を見ます。
